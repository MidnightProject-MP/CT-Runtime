# GAS Prototype Schema

The workbook contains `executions`, `work_orders`, `wakes`, `continuations`, `observer_ledger`, `memory`, `lessons`, `identity_signals`, `foundry_signals`, `model_telemetry`, `evidence`, `chronicle`, and `schema`. Rows are immutable facts; revisions reference `supersedes`, and SHA-256/Drive file IDs identify artifacts. IDs are deterministic hashes, never row numbers. A continuation is schema `ct-continuation-v1`: bounded semantic context, not transcript replay, retaining one logical work-order ID across physical executions.

The adapter is a serialized single writer guarded by `LockService`; lock-wrapped public mutations call unlocked primitives and never nest locks. Sheets and Drive are the only reconstruction sources. A record's latest valid revision is selected deterministically, and idempotency, supersession, lifecycle, owner, fence, and expiry conflicts fail closed. Observer semantic processing remains pending unless explicitly invoked as a bounded, non-recursive model turn.

Wake reasons include `requested`, `maintenance`, `recovery`, `model-deferred`, `checkpoint`, `ci`, `worker`, `api`, `model-quota`, `scheduled`, and `human`. One recurring safety trigger scans due wakes under a check-and-create lock; it is not an orchestration scheduler and no `runWake` trigger is created. Work orders may be `waiting` or `deferred` with a persisted resume condition. Preemption telemetry records budget, actual and checkpoint duration, continuation, repeat/loss, operation, all logical IDs, and exact capability reason without raw secrets or transcripts. Duration never sets `general_compute_requested`.

Inference telemetry is one bounded normalized row per attempted provider call. It records logical work order and physical execution, role/task purpose, requested/canonical/actual provider and model, request/response timestamps and latency, HTTP/error and normalized failure class, retry count and fallback path, and only authoritative scalar usage/context/cost/quota signals. Provider responses and prompts are not telemetry. Terminal quota, balance, model, context, and request failures do not generate automatic retries; they either checkpoint an explicitly eligible free-only fallback or leave a durable `waiting` continuation for a later state-change signal.

## Feedback interface versus durable record

The `Feedback` tab is an 8-column human interface contract (`SHEET_HEADERS`, `HEADER_ROW = 4`, `DATA_FIRST_ROW = 5`, named `COL` positions in `gas_feedback.js`); it is not a reduced positional view of the durable work order. The durable feedback work-order payload carries 13 semantic fields (`work_order_id`, `goal`, `step`, `model`, `physical_execution_count`, `feedback_thread_id`, `feedback_message_id`, `feedback_revision`, `feedback_fingerprint`, `project`, `reply_to`, `launch_context`, `resume_context`). Mapping is semantic only: human project/message/reply/revision plus deterministic thread and message derivation produce the durable goal and linkage; lifecycle and response project back to the system-written status and update columns; thread assignment, fingerprint, identifiers, model binding, and launch/resume context are Runtime-generated with no human cell. Positional equivalence between the 8 human columns and the 13 durable fields is prohibited; the adapter fails closed unless row 4 carries exactly the canonical header and never admits row 4 as a message.
